From Wallet Seed to Ethereum Address: Hashing, Key Derivation and Cryptographic Primitives

An Ethereum address is built from a 12-word mnemonic in six deterministic steps. Each step uses a different tool because each solves a different problem: key management, public-key cryptography, hashing and error detection.

1 The pipeline at a glance

Six steps turn 12 words into one address, each with a different tool. Each box is the form the data takes; each arrow is a step, named with its tool and the kind of job it does.

1. Mnemonic phrase 12 or 24 words from BIP-39 wordlist (128–256 bits entropy)
Starting Input
BIP-39 Key management: Words stretched with PBKDF2-HMAC-SHA512 (2048 iterations) into a 512-bit seed
2. Seed 512 bits (64 bytes raw binary)
Intermediate
BIP-32 & BIP-44 Key management: HMAC-SHA512 builds HD key tree; derivation path picks the account
3. Private key 256 bits (32 bytes), kept strictly secret
Confidential Secret
secp256k1 Public-key cryptography: Q = k·G on the curve: easy forward, infeasible to reverse (ECDLP)
4. Public key 64 bytes: uncompressed x and y coordinates (excluding 0x04 prefix)
Public Point
Keccak-256 Hashing: Hash the 64-byte public key and keep the last 20 bytes (40 hex chars)
5. Ethereum address 20 bytes (40 lowercase hex characters)
Raw Identifier
EIP-55 Checksum: Capitalize letters matching hash nibbles ≥ 8 (detects typos, value unchanged)
6. Checksummed address 0x prefix + mixed upper/lower case hex string (e.g. 0x5aAeb605...)
Final Safe Output

2 Role of each standard and primitive

BIP-39: mnemonic and seed. The wallet generates random entropy (128 bits for 12 words, 256 bits for 24). It appends a short checksum taken from the SHA-256 hash of the entropy (4 or 8 bits) and splits the result into 11-bit groups, each mapped to a word from a fixed list of 2048 words. The mnemonic, plus an optional passphrase, goes through PBKDF2-HMAC-SHA512 (2048 iterations) and produces a 512-bit seed. Same phrase and passphrase always give the same seed.

BIP-32: hierarchical deterministic (HD) keys. HMAC-SHA512 turns the seed into a master key and a chain code. Every parent key can deterministically derive child keys, which forms a tree. One backup of the seed restores every key. "Hardened" derivation (marked with an apostrophe) stops someone who knows a child private key and the parent's extended public key from recovering the parent private key.

BIP-44: standard derivation paths. It fixes the structure m / purpose' / coin_type' / account' / change / address_index. For Ethereum the first account is m/44'/60'/0'/0/0 (60 = Ethereum, 0 = Bitcoin). Thanks to this standard, MetaMask, Rabby, Exodus or Rainbow find the same addresses from the same mnemonic.

secp256k1: public-key cryptography. The elliptic curve y² = x³ + 7 over a finite field of about 2²⁵⁶ elements. The public key is Q = k·G, where k is the private key and G is the fixed base point. Going back from Q to k means solving the Elliptic Curve Discrete Logarithm Problem (ECDLP), which is considered infeasible. The same curve is used for digital signatures (ECDSA): whoever knows k signs, anyone can verify with Q. HMWK 1 shows this idea on a toy curve.

Keccak-256: hashing. The address is the last 20 bytes (40 hex characters) of the Keccak-256 hash of the 64-byte public key (x ‖ y, without the 0x04 prefix).

EIP-55: checksum. Compute Keccak-256 of the lowercase address (without 0x, as ASCII text). For each letter a–f of the address, if the matching hex digit of the hash is 8 or more, write the letter in uppercase. Example from the EIP-55 specification: 0x5aAeb6053F3E94C9b9A09f33669435E7Ef1BeAed. The value of the address does not change, but a typo breaks the capitalization pattern and the wallet can warn the user. A random typo goes unnoticed with probability about 2⁻ⁿ, where n is the number of letters in the address (on average about 15, so roughly 1 in 32,000).

3 Five concepts that are easy to confuse

Concept What it is Where it appears
Key generation Generation Creating something new and random The initial entropy of BIP-39
Key derivation Derivation Computing keys deterministically from an existing secret PBKDF2 (seed), BIP-32 and BIP-44 (child keys)
Public-key cryptography Asymmetric A private/public key pair for signing and verifying secp256k1
Hashing One-way A keyless, one-way function with a fixed-size output Keccak-256 (and SHA-256/SHA-512 inside BIP-39 and BIP-32)
Checksum Integrity Detects accidental errors; protects nothing against attackers BIP-39 checksum, EIP-55
Encoding Format Another way to write the same data; no security at all BIP-39 words, hexadecimal, the 0x prefix
Key takeaway: Checksums and encodings give neither confidentiality nor authenticity. A hash is not encryption (it cannot be decrypted) and it is not a signature.

4 Historical context

Foundations date from 1977 and 2001; wallet standards came in 2012–2016. The chronological timeline below illustrates the 7 key milestones to scale:

timeline · 7 milestones, 1977 to 2016, to scale

Colours match the pipeline picture. SHA-512 (part of SHA-2) is used inside BIP-39 and BIP-32, and Keccak won the NIST competition in 2012 before becoming SHA-3.

The logical order is: basic cryptographic tools first (RSA, SHA-2), then the key-management standards born in Bitcoin (BIP), then Ethereum-specific choices (Keccak-256, EIP-55). Ethereum launched in 2015, before the final SHA-3 standard, and adopted the earlier Keccak version. It also inherited the secp256k1 curve from Bitcoin.

5 SHA-2 / SHA-512 versus Keccak / SHA-3

Both are cryptographic hash families, but their internal designs are unrelated. SHA-2 (2001) uses the Merkle–Damgård construction. SHA-3 is based on Keccak, which uses the sponge construction, and was chosen as an independent alternative in case SHA-2 were ever weakened.

Ethereum uses Keccak-256, which is not identical to SHA3-256. During standardization NIST changed the domain-separation and padding rule (SHA3 appends the bits 01 before padding; original Keccak does not). The internal permutation is identical, but the final outputs completely differ:

Function Hash of the empty string (ASCII "")
Keccak-256 (Ethereum) c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
SHA3-256 (NIST) a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

Critical consequence: In practice, using SHA3-256 instead of Keccak-256 produces completely wrong Ethereum addresses.

6 Why several primitives instead of one?

Each tool in the pipeline has a specific mathematical specialty:

  • BIP-39 / BIP-32 / BIP-44 → key management: one backup, an ordered key tree, compatibility across wallets.
  • secp256k1 → private/public relation and signatures: needs rich algebraic group structure that allows public verification, which a hash cannot offer.
  • Keccak-256 → hashing: compresses the 64-byte public key into 20 uniform, scrambled bytes.
  • EIP-55 → error detection: adds no extra length (still 40 characters) and is fully backwards-compatible with lowercase addresses.

Separation of Roles Principle: Every primitive is optimized for one task, can be analyzed and audited independently, and a weakness in one layer stays confined to that layer.

7 Statistical properties

  • Hash functions (Keccak, SHA-2): Avalanche effect (about 50% of output bits flip when one input bit changes), output indistinguishable from uniform, no visible correlation between input and output. Two very similar public keys produce completely unrelated addresses.
  • secp256k1: Not a hash. The relation (k+1)G = kG + G is strictly algebraic; security comes solely from the hardness of the ECDLP, not from scrambling bits (as explored in HMWK 1).
  • Mnemonic and seed: Security depends strictly on the entropy: 128 bits for 12 words (2¹²⁸ possibilities). The 512-bit seed adds no extra entropy beyond the original phrase.
  • EIP-55: The capitalization pattern is a pseudo-random sample of hash bits, so each letter has an independent ~1/2 probability of being uppercase.

Change the private key by just one unit (last digits ...ff80 become ...ff81):

0 bits flipped Ideal: 50% (80 bits) 160 bits flipped

Result: 85 of the 160 address bits differ (53.1%), remarkably close to the ideal 50% avalanche effect of a cryptographic hash function! Inside secp256k1 alone the relation (k+1)G = kG + G is visible; the Keccak-256 hash completely hides it.

Key Observations from the Example:
  1. One random choice, then only deterministic steps. Randomness is only in step 0; steps 1 to 6 are derivation, curve math, hashing and checksum.
  2. Avalanche in action: 53.1% bit difference hides algebraic curve relationships.
  3. Keccak-256 ≠ SHA3-256: Hashing the same public key with NIST SHA3-256 gives 8ed30a8892bc3cb25ca6b52d045b51f176f55913, a completely wrong address.
  4. Everything moves forward only, except the checksum which can be reversed simply by lowercasing.

10 Conclusion

Pipeline Step Kind of primitive Can it be reversed?
Phrase to seed (BIP-39) Derivation built on a hash (PBKDF2) Not in practice (2048 rounds of HMAC-SHA512)
Seed to private key (BIP-32, BIP-44) Derivation built on a hash (HMAC) Not in practice (HMAC-SHA512 one-wayness)
Private key to public key Public-key cryptography (secp256k1) No (needs ECDLP, infeasible at 256 bits)
Public key to address Hash (Keccak-256) No (pre-image resistant; 12 bytes thrown away)
Address to checksummed address Checksum over an encoding (EIP-55) Yes (just convert to lowercase)

This is why the 12 words restore every account, while nobody can go from an address back to the phrase. One random choice, five one-way steps and a checksum that only protects against typos.

Conclusion: The worked example above ran the whole chain on real values. The pipeline combines primitives with different roles: deterministic key derivation (BIP), public-key cryptography (secp256k1), hashing (Keccak-256) and a checksum (EIP-55). Keeping generation, derivation, hashing, checksums and encoding separate avoids common confusions. Desirable statistical properties such as avalanche and uniformity belong to hash functions, while public-key cryptography relies on hard mathematical problems.
